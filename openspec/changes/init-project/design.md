# Design

## Context

项目已实现第一版（Astro 7 + React 19 + TypeScript strict + Tailwind v4 + Zod 4 + pnpm；GitHub Pages 部署已线上运行）。本 change 用 OpenSpec 规格化整个项目的行为基线。设计需服务的目标：长期维护、数据正确性优先、成本趋零（GitHub 免费基础设施）、可被 ChatGPT 连接器增量写入。动机详见 proposal.md「Why」。

## Goals / Non-Goals

**Goals:**
- 数据契约机器可读且可校验：Schema 版本化、业务约束、稳定 ID、幂等合并。
- 人工与自动化共用同一写入协议（补丁 + 合并工具），任何失败不落盘。
- 网页完全静态、可离线部署、无运行时后端。
- 部署与个人状态均无需账号系统。

**Non-Goals:**
- 不引入后端服务器、数据库、Redis、付费 SaaS。
- 不在浏览器暴露 GitHub Token；不建登录体系。
- 本 change 不实现新功能，只建立规格基线并核对现有实现。

## Decisions

### D1: 静态 SSG + Git 仓库作为唯一数据源
- 选择：Astro 静态生成，`data/radar.json` 单文件权威源；网页构建时读取并内联数据。
- 理由：GitHub Pages/Cloudflare 均可免费托管；无运维面；数据与发布同仓库同历史。
- 备选：服务端渲染 + API/数据库 → 依赖常驻后端，违反成本目标，否决。

### D2: 单文件数据 + schemaVersion 迁移机制
- 选择：约定 `schemaVersion`（当前 1），并提供合并/校验工具链；规模增长后用同一工具拆分（保留稳定 ID 与去重语义）。
- 理由：ChatGPT 连接器每次写入一个文件成本最低；过早拆数百小文件会放大 GitHub 操作。
- 风险：单文件体积变大 → 以 warning 记录规模阈值，迁移由工具链完成，不改变对外契约。

### D3: 双层校验（Zod Schema + 业务约束）与发布阻断
- 选择：解析阶段 Zod 校验结构/枚举，应用阶段独立业务约束（孤立活动、单位-额度矛盾、时间倒挂、demo 不得标官方等）。
- 理由：结构错误与业务错误分离，错误信息定位到条目；CI `pnpm validate` 退出非零即阻止发布。
- 备选：仅 JSON Schema → 无法表达跨字段约束（如 amountType/resetInterval 一致性）。

### D4: 稳定 ID 与幂等增量合并
- 选择：平台 ID=slug；活动 ID=`{slug}:{base36(fnv1a(去重键))}`；合并引擎对字段 diff 自动生成 ChangeEvent；事件/运行按指纹去重；结果校验失败即回滚。
- 理由：跨轮去重不依赖模型记忆；重复执行安全（幂等）；历史完整（旧事件不被覆盖）。
- 备选：标题去重 → 同平台多权益会误合并，否决。

### D5: React 交互 + 自研轻量组件
- 选择：Astro 负责路由/SSG，React hydrate 承载搜索、筛选、视图切换、个人操作、图表；UI 组件自研（Button/Badge/Card 等，CSS 变量语义色），图表用纯 SVG。
- 理由：避免引入大 UI 库与图表库，控制体积，保持可访问性语义（aria、焦点环）。
- 备选：shadcn/ui → 本质为源码复制，收益与自研持平，额外依赖无必要。

### D6: localStorage 个人状态版本化信封
- 选择：`{version, favorites, claims}` 信封；读取时迁移兼容旧版本，未来版本拒绝读取；导入导出复用同一信封。
- 理由：无后端时可长期演进；拒绝未来版本可防降级损坏。

### D7: 自动化写入协议 = 补丁 + 事务性合并
- 选择：ChatGPT 生成完整补丁（platforms/upserts/ends/events/runs），`scripts/merge.ts` 读取当前数据、校验基线、合并、整体校验、原子写（tmp+rename）；冲突时重读最新并重合并。
- 理由：连接器只做“读-生成-提交”；复杂判定收敛到可测试的合并引擎。
- 审批模式：无法无人值守写入时，生成待导入补丁，绝不伪装成功。

### D8: GitHub Pages 子路径 base 处理
- 选择：构建 base 由仓库名自动推导；所有内部导航经 `withBase()` 工具统一拼接，避免手写绝对路径丢失前缀。
- 理由：GitHub Pages 项目站点运行在 `/repo/` 下；Astro 不会自动改写手写绝对路径（线上已出现该故障并修复）。
- 备选：仅用相对路径 → 不同页面深度解析不一致，否决。

### D9: 部署双通道
- 选择：GitHub Pages（公开仓库，官方 CI）为主；Cloudflare Pages（私有仓库场景）无代码改动备选。
- 理由：私有仓库免费计划不支持 Pages；保留两通道不影响数据契约。

## Risks / Trade-offs

- [ChatGPT 写入质量不稳定（如运行记录漏填提交哈希、状态字段保守）] → 合并引擎强制校验；监控页如实呈现；将协议写入 prompt 文档并逐步收紧。
- [子路径部署回归] → E2E 断言内部链接前缀；CI 在两种 base 下构建验证。
- [演示数据与真实数据混杂] → 实体带 `demo` 标记且禁止标官方确认；页面横幅明示；正式数据经合并引擎进入。
- [单文件 radar.json 体积增长] → 监控阈值，出现时用工具链拆分归档，保持对外协议不变。
- [连接器审批不稳定导致更新延迟] → 页面与监控状态如实反映，不伪装成功；提供人工合并入口。

## Migration Plan

1. 本 change 归档时，将 5 个能力规格合并进 `openspec/specs/`。
2. 对照规格核对现有实现：数据协议（已完成）、监控（补运行记录回读验证）、网页（已完成）、个人状态（已完成）、部署（已完成）。
3. 规格化的验收项转化为任务；差异项形成最小修改集。

## Open Questions

- 是否启用设置通知（RSS/邮件）以及触达渠道（可在后续 change 决策）。
- 数据文件拆分的触发规模阈值（如单文件 > 2MB 或活动数 > 2000，可在增长时定）。
- 账号同步（多设备）时机（规格已约束为本地，未来独立 change 演进）。
