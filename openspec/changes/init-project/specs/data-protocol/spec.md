# Spec Delta

## Purpose

定义 AI Free Radar 权威数据文件 `data/radar.json` 的实体结构、校验规则、稳定 ID、去重合并与事件追溯，确保自动化写入与人工维护共享同一份可验证的数据契约。

## ADDED Requirements

### Requirement: 权威数据文件与 Schema 版本

系统以仓库内 `data/radar.json` 为唯一权威数据源。文件必须包含 `schemaVersion`（当前为 1）、`lastSuccessfulSync`、`platforms`、`offers`、`events`、`runs` 六个顶层成员。任何读取、合并或发布流程发现 `schemaVersion` 不匹配或数据无法通过 Schema 校验时，必须拒绝使用该数据并报告错误，不得静默忽略。

#### Scenario: 读取合法数据

- **WHEN** 读取 `data/radar.json` 且其结构与 schemaVersion=1 匹配
- **THEN** 系统使用该数据渲染页面与统计

#### Scenario: 版本不匹配

- **WHEN** 数据文件 `schemaVersion` 不等于 1
- **THEN** 系统拒绝解析，并给出明确错误，不产生任何页面输出或写入

#### Scenario: 缺少必需顶层成员

- **WHEN** 数据文件缺少 `offers` 或 `runs` 等必需成员
- **THEN** 系统判定数据非法并拒绝使用

### Requirement: 实体字段与枚举约束

平台（Platform）与活动（Offer）必须满足：活动归属存在的平台（platformId 引用有效平台）；额度 `amount` 与 `unit` 一致（Unlimited/Unknown 单位时 amount 必须为空）；`amountType` 与 `resetInterval` 语义一致；结束时间不早于开始时间；每个活动至少包含一个证据来源。枚举取值必须来自受控集合（单位、额度类型、接入方式、可信度、活动状态、事件类型、运行状态等），禁止枚举外取值。

#### Scenario: 孤立活动被拒绝

- **WHEN** 某活动 `platformId` 指向不存在的平台
- **THEN** 数据校验失败并列出该活动

#### Scenario: 单位与额度矛盾被拒绝

- **WHEN** 活动单位标记为 Unlimited 但额度为非空数值
- **THEN** 数据校验失败

#### Scenario: 活动缺失证据来源被拒绝

- **WHEN** 活动 `sources` 为空数组
- **THEN** 数据校验失败

### Requirement: 稳定 ID 与去重

同一平台活动必须拥有稳定 ID：平台 ID 由其 slug 确定，活动 ID 由平台域名、活动名、模型范围、权益类型、单位、领取渠道、地区与周期规范化生成。同一活动额度、截止日期或状态变化时，系统必须更新原条目并追加变更事件，禁止创建重复条目。同一补丁重复提交两次不得产生重复活动、重复事件或重复运行记录。

#### Scenario: 重复提交幂等

- **WHEN** 同一增量补丁连续应用两次
- **THEN** 第二次不新增任何活动、事件或运行记录，数据与前一次结果一致

#### Scenario: 更新已有活动

- **WHEN** 补丁携带已有活动 ID 且字段值变化
- **THEN** 原活动的对应字段被更新，并生成一条变更事件

### Requirement: 额度不可跨单位比较

系统不得直接将不同单位（如 Credits 与 Tokens、USD 与 CNY）的额度数值相互比较或排序；任何基于价值的排序、推荐或统计都只能在相同量纲内进行。

#### Scenario: 排序保持单位隔离

- **WHEN** 展示或排序不同单位的活动
- **THEN** 系统只在同一单位分组内部做价值比较，不跨单位换算

### Requirement: 可信度与活动状态分离

平台可信度（官方确认/社区实测/待核实）与活动状态（有效/即将开始/已结束/暂停/状态未知）必须作为独立字段分别记录；历史上曾官方确认的活动不代表当前仍有效，页面必须使用最近核验时间与核验结果呈现新鲜度。

#### Scenario: 待核实与有效状态并存

- **WHEN** 一个活动状态为“有效”但核验状态为“待核实”
- **THEN** 页面同时显示两者，且不将该活动计为已验证有效资源

### Requirement: 未确认信息显式呈现

任何无法确认的字段（额度、截止日期、绑卡、实名、地区、速率限制、上下文、API 兼容等）必须显式显示为“未确认”，系统不得自行推断或填造数值。

#### Scenario: 缺失字段显示未确认

- **WHEN** 活动缺少截止日期且状态未知
- **THEN** 页面在对应字段显示“未确认”而非猜测值

### Requirement: 变更事件与历史保留

系统必须为每次重要变化记录事件：事件包含时间、类型、所属活动/平台、字段、原值、新值与证据来源。历史事件不得被后续更新覆盖或删除；页面必须能够展示原值与新值以供追溯。

#### Scenario: 多次更新保留历史

- **WHEN** 同一活动经历两次以上字段变化
- **THEN** 每条变化均有独立事件，且各事件保留各自的原值与新值

### Requirement: 数据校验工具

项目必须提供数据校验命令：校验失败时报告具体条目与字段并返回非零退出码；仅出现警告时允许通过。校验结果用于决定是否允许发布。

#### Scenario: 校验失败阻止发布

- **WHEN** 数据校验存在错误
- **THEN** 发布流程中止，且不自动删除或修改任何历史数据

### Requirement: 增量合并与冲突处理

系统必须提供增量合并能力：应用补丁前读取并校验现有数据，合并后再次整体校验；任何阶段失败都不得写入文件。若目标文件被并发修改，必须重新读取最新数据并重新合并，禁止强制覆盖。

#### Scenario: 合并失败回滚

- **WHEN** 合并结果校验失败
- **THEN** 数据文件保持原状，命令返回失败并说明原因

#### Scenario: 并发冲突重放

- **WHEN** 基于旧基线生成的补丁在最新数据上重放
- **THEN** 系统重新合并，最终数据包含双方新增内容且无重复条目，不覆盖并行写入的结果
